================================================================================
一、项目概述
================================================================================

Enbon 综合管理后台系统 是一款为 LED 显示屏幕外贸公司开发的内部一体化
办公平台(OA/CRM/HR),目标统一文件存储、客户关系管理、人力资源管理和共
享办公入口。

技术栈:
  - 后端: NestJS 11 + TypeScript + TypeORM
  - 前端: Vue 3 (Composition API) + TypeScript + Element Plus 2.11
  - 数据库: PostgreSQL 16(生产) / SQLite(开发)
  - 认证: JWT + bcrypt
  - 存储: MinIO(可选) / 本地磁盘
  - 缓存: Redis(可选)
  - 构建: Vite 7(前端) / Nest CLI(后端)

代码规模:
  - 后端: 约 38 个模块,160+ TypeScript 源文件
  - 前端: 约 70+ 个组件/视图,30 个 API 模块
  - 数据库: 64 个实体/表
  - 总代码量估计 5-8 万行

四、权限系统分析
================================================================================

4.1 双层权限架构

系统实现了两套并行的权限系统，登录时合并:

  系统A - RBAC(基于角色):
    角色模板(Role) → 角色权限(RolePermission) → 权限码(Permission)
    用户角色(UserRole)绑定用户到角色
    11个预置角色模板(super_admin_role, sales_dept_manager_role等)

  系统B - 岗位权限引擎(基于岗位):
    部门(DepartmentConfig) → 岗位(PositionConfig) → 岗位权限(PositionPermission)
    7个部门, 52个岗位, 每个岗位预配置权限码
    支持部门模块可见性(DepartmentModule)

4.2 权限码体系
  约169个权限码, 按模块分级:
    system.*      - 系统管理
    employee.*    - 员工管理
    crm.*         - 客户关系管理
    hr.*          - 人力资源管理
    files.*       - 文件管理
    workspace.*   - 工作区
    finance.*     - 财务
    report.*      - 报表
    request.*     - 物料申请
    workgroup.*   - 工作组

  支持通配符: hr.* 匹配 hr.attendance.view 等所有子权限

4.3 认证流程
  1. 支持 username / loginUsername / phone 三种方式登录
  2. bcrypt 10轮密码验证
  3. 自动分配角色模板(基于UserRole枚举)
  4. 自动分配岗位权限(基于position字段)
  5. 合并RBAC + PositionEngine权限码
  6. 计算visibleModules + dataScopes
  7. 签发JWT(24h, 记住我7d)

4.4 鉴权流程(每次请求)
  AuthGuard(全局) → 验证JWT → 查询用户权限 → 注入request.userContext
  PermissionsGuard(全局) → 读取@RequirePermissions → 通配符匹配 → 拒绝/放行

4.5 前端权限
  useUserStore提供以下getter:
    hasPermission(code)       - 单一权限检查
    hasAnyPermission(codes)   - 或逻辑
    hasAllPermissions(codes)  - 且逻辑
    canAccessModule(module)   - 模块可见性
    canAccessModuleData(module) - 数据范围检查

4.6 数据范围(DataScope)
  三级: SELF(本人) / DEPARTMENT(部门) / ORG(全组织)
  在Service层通过applyDataScopeFilter()应用

十、安全性分析
================================================================================

10.1 已发现的安全问题

  [严重] StorageController未认证用户默认使用userId=1
    位置: backend/src/modules/storage/storage.controller.ts
    问题: 所有端点使用 userId = (req as any).user?.id || 1,
         未认证请求被静默视为超级管理员(id=1)。
    影响: 攻击者可以无认证上传/下载/删除/分享任意文件。

  [严重] Files上传端点无路径穿越检查
    位置: backend/src/modules/files/files.controller.ts uploadFile
    问题: 上传构建targetDirPath但从未验证结果在drive.path内,
         攻击者可通过path=../../Windows/System32写入任意文件。
    影响: 可能导致服务器被完全控制。

  [严重] Files预览端点从driveId构建回退根路径
    位置: files.controller.ts previewFile
    问题: 当getDriveInfo失败时,从driveId首字母构建盘符路径,
         如driveId=a则解析到A:\。可读取任意驱动器文件。
    影响: 任意文件读取漏洞。

  [严重] 无Rate Limiting
    所有端点(包括登录接口)无速率限制,易受暴力破解攻击。
    没有使用@nestjs/throttler包。

  [严重] 无安全响应头(Helmet)
    未设置X-Content-Type-Options, X-Frame-Options, CSP等安全头。

  [严重] 明文密码存储(前端)
    Login.vue的"记住我"功能将用户密码明文存入localStorage(key: enbon_login_info)。
    任何XSS漏洞或物理访问都会导致密码泄露。

  [严重] 调试端点暴露(@Public)
    GET /api/permissions/debug/permissions        - 暴露全部权限码
    GET /api/permissions/debug/hr-director-perms  - 暴露HR总监权限
    GET /api/permissions/diagnostic/hr-director   - 暴露用户诊断信息
    这些端点未受身份验证保护。

  [高危] 文件预览/缩略图/下载端点无鉴权
    GET /files/preview, GET /files/thumbnail, GET /files/download
    虽然前端附加了token查询参数,但后端从不验证。

  [高危] 无CSRF保护
    纯JWT Bearer认证,未使用CSRF Token或SameSite Cookie。

  [高危] 无请求体大小限制
    express.json()使用默认100kb,但Excel导入端点接受任意大小。

  [中危] Email预览XSS风险
    frontend/src/components/crm/EmailModule.vue使用v-html渲染邮件正文。

  [中危] IMAP TLS验证禁用
    email-sync.service.ts设置rejectUnauthorized: false。

  [中危] 硬编码默认凭据
    .env中: JWT_SECRET=your-secret-key-change-in-production
           DB_PASSWORD=EnbonAdmin2026
    users.service.ts: 默认admin密码=EnbonAdmin2026
    User实体: PASSWORD_ENCRYPTION_KEY默认='development-key-32-bytes-long!!'

  [中危] CORS开发模式全开放
    origin: true(开发环境)反射所有来源。

  [中危] forbidNonWhitelisted: false
    请求体中的未知字段被静默丢弃,可能掩盖API误用。

  [中危] WorkspaceAdmin控制器无任何权限装饰器
    多个CRUD端点使用@Body() body: any,零验证。

10.2 做得好的安全措施
  - JWT + bcrypt(10轮)密码哈希
  - 全局AuthGuard + PermissionsGuard双重保护
  - 文件路径穿越防护(startsWith检查)
  - 全局异常过滤器生产环境隐藏500错误详情
  - 参数化SQL查询防注入
  - AES-256-GCM加密公司账户密码
  - DTO使用class-validator验证

十一、BUG与缺陷清单
================================================================================

*表示严重程度: [严重]=CRITICAL [高]=HIGH [中]=MEDIUM [低]=LOW

--- 权限系统 ---

[严重] StorageController未认证用户默认userId=1
  位置: storage.controller.ts 所有端点
  问题: userId = (req as any).user?.id || 1,未认证直接当超管操作。
  影响: 无认证可上传/下载/删除任意文件。

[严重] AuthGuard仅查询RBAC权限,遗漏PositionEngine权限
  位置: backend/src/common/guards/auth.guard.ts:96
  问题: AuthGuard只调用permissionsService.getUserEffectivePermissions()
        (RBAC路径),未合并PermissionEngineService的岗位权限。导致仅通过
        岗位分配的权限在守卫层面被拒绝。
  影响: 所有非RBAC角色的岗位权限在API层面不生效。
  修复: AuthGuard也应调用PermissionEngineService合并权限。

[严重] audit.view权限码未写入种子数据
  位置: backend/src/modules/permissions/permissions.service.ts
  问题: AuditLogController要求@RequirePermissions('audit.view'),
        但该权限码在seedPermissionsAndRoles()中未定义。
  影响: 非超管用户永远无法查看审计日志。
  修复: 在seed数据中添加audit.view权限码定义。

[严重] DENY授权类型从未生效
  位置: UserExtraPermission和PositionPermission实体
  问题: grantType字段支持'DENY',但所有权限查询仅过滤grantType:'GRANT',
        DENY被完全忽略。
  影响: 如果管理员想撤销某用户的特定权限无法实现。
  修复: 在权限合并逻辑中添加DENY优先处理。

[严重] system.permission.manage未写入种子数据
  位置: permissions.controller.ts:401
  问题: reseed()端点使用@RequirePermissions('system.permission.manage'),
        但该权限码未在种子数据中定义。
  影响: 仅超管可访问(虽可能是设计意图,但权限码不应缺失)。

[高] 权限合并逻辑有二义性
  位置: auth.service.ts:127-128
  问题: RBAC权限和PositionEngine权限简单合并去重,未处理来源优先级
        和数据范围差异。

--- HR模块 ---

[严重] 路由重复定义导致死代码(所有P1增强端点不可达)
  位置: hr.controller.ts
  问题: POST/GET /performance/templates在124行和798行各定义一次,
        NestJS使用先定义的,第二套(含cycles/indicators/reviews/pip
        等14+端点)完全不可达。P1增强绩效系统形同虚设。
  修复: 删除重复路由或合并为单一实现。

[严重] stableRandom用于生产数据造假
